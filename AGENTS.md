# Engineering and editorial rules

- Plica is an independent knowledge base about the meta-architecture of real software systems, not Petwins runtime code, AI news, interview preparation, or the retired Stackworthy prototype.
- Keep backend content and frontend presentation independently buildable. Backend uses the Python standard library and imports no UI. A replacement UI is separately authorized work; never make its framework a backend dependency or create duplicate content authorities.
- Edit `backend/content/` and `backend/skills/plica-architecture/SKILL.md` for content. The published UI lives in `frontend/prototype/src/`; `frontend/build.py` and `frontend/assets/` retain the static parity reference. Frontend consumes only the documented exported catalog, not backend imports/source files. Root `build.py` composes independent releases; `site/`, `dist/` and `frontend/prototype/release/` are generated snapshots, never editing authorities.
- Preserve Production versus Research. A thematic relationship is not evidence of deployment. Cite original sources with dates, distinguish editorial interpretation, and do not invent metrics, authorship, system internals or verification results.
- Case–term edges are reviewed entries in `backend/content/relations.json`, not automatically inferred from word matches. Review both ends of every changed relation.
- Do not republish third-party full text, illustrations or other assets without documented permission. Follow `docs/licensing.md`; public visibility is not a blanket license grant.
- Never commit credentials, private configuration, personal data or confidential architecture. No model-provider keys in client JavaScript. AI responses, accounts, payments, newsletter and sponsorship services remain unimplemented.
- Preserve Drive archives and genuine Git history. No forged historical commits, force pushes, destructive cleanup, or migration of unrelated assets.
- Before publishing, run `python3 -m unittest discover -s tests -v`, `python3 validate_content.py`, `python3 build.py`, `node --check site/assets/site.js`, and `python3 test_site.py`. Exercise actual HTTP navigation at root and `/plica/`, desktop/mobile, filters/search, graph/glossary links, detail pages and the preview sidebar. Recheck affected behavior after edits.
- Keep CI and deployment on these same scripts. Composed static production hosting needs no Python runtime. The independent read-only API development server is not a deployed account/AI/payment backend; Playwright remains test-only. Preserve old public API contracts and document new versions in `docs/api.md`.
- GitHub Pages publishes `python3 build.py --frontend react` output from `frontend/prototype/release/` after validation. Install locked UI dependencies with `npm ci --prefix frontend/prototype`; keep the default static build and its acceptance checks as a compatibility reference.
- Report separately: implemented, tested locally, verified in CI, deployed, and verified live. Never mark skipped or blocked tests as passed. A successful build alone does not prove working interaction, source accuracy, licensing clearance, or deployment.
